## Goal

The files in `data/` are the only source of truth (design principles 1 and 2). One command turns them into dumps and a Postgres database that Supabase serves to the site and API, and CI proves on every pull request that it works from an empty database.

## Command

`uv run python -m build [--data data] [--out dist] [--database URL]`

1. **Validate:** run every `checks files` rule. Any finding prints and stops the build with status 1; nothing is written.
2. **Compute edges** from connectivity claims.
3. **Write dumps** into a fresh temporary folder, then replace `--out` with it, so a failed build never leaves half a dump. `dist/` is git-ignored.
4. **Load Postgres** if a database URL is given (`--database`, else the environment variable `AXONARIUM_DATABASE_URL`, so secrets stay off command lines): in one transaction, empty the project's tables and insert every row. Readers see the old data or the new, never a mix. The build never changes the schema (see Schema).

Output is deterministic: rows sorted by ID, no timestamps.

## Tables

All in the `public` schema, which Supabase's REST API serves. Enum values are stored as text (the checks have validated them). Nested parts that the site shows but doesn't filter on are JSONB.

| Table | Key | Columns |
| --- | --- | --- |
| `atlases` | `id` | `name`, `species`, `version`, `url`, `brainglobe_name`, `extra` |
| `regions` | `id` | `name`, `acronym`, `atlas` (→ `atlases`), `parent`, `uberon`, `synonyms` (text[]), `extra` |
| `neuron_types` | `id` | `name`, `species`, `region_type`, `region_id`, `region_atlas`, `transmitter`, `markers` (text[]), `cell_ontology`, `synonyms` (text[]), `extra` |
| `sources` | `id` | `title`, `year`, `journal`, `license`, `open_access`, `retracted`, `extra` |
| `connectivity_claims` | `id` | `subject_type`, `subject_id`, `subject_atlas`, `predicate`, `object_type`, `object_id`, `object_atlas`, `species`, `evidence_class`, `result`, `sign`, `strength`, `measurements` (JSONB), `source_key` (→ `sources`), `doi`, `pmid`, `pmcid`, `arxiv`, `locator`, `paraphrase`, `excerpt`, `curation` (JSONB), `verification` (JSONB), `status`, `extra` |
| `homology_claims` | `id` | `subject_type`, `subject_id`, `subject_atlas`, `subject_species`, `object_type`, `object_id`, `object_atlas`, `object_species`, `correspondence`, `confidence`, `basis` (text[]), the same citation, text, curation, status and `extra` columns |
| `edges` | `id` | see below |
| `retractions` | `position` | `claim`, `action`, `reason`, `curation` (JSONB) |

`extra` is JSONB everywhere. `source_key` is the claim's source record ID (sprint 0.3c).

**Edges** aggregate the connectivity claims that aren't `retracted`, one edge per subject, predicate, object and species. `id` is `<subject_id>|<predicate>|<object_id>|<species>`. Columns: `subject_id`, `subject_type`, `predicate`, `object_id`, `object_type`, `species`, `n_claims`, `n_present`, `n_absent`, `n_ambiguous`, `n_disputed`, `evidence_classes` (sorted, distinct), `strength` (the strongest ordinal strength among present claims: weak < moderate < strong; null if none), `signs` (sorted, distinct), `claim_ids` (sorted). Edges are never edited by hand.

## Schema

The tables are defined once as SQLAlchemy tables in `build/tables.py` and created by Alembic migrations in `build/migrations/` (generated with `alembic revision --autogenerate`, reviewed, and applied with `alembic upgrade head` by CI and by the deploy job before each build; CI also runs `alembic check`). A load into a database behind `build/tables.py` fails and names `alembic upgrade head`. The baseline migration also gives Supabase's `anon` and `authenticated` roles row-level security with one `select` policy per table and revokes every other privilege (it creates those roles on a plain Postgres). The load empties the tables without `cascade`, so views on them survive and a foreign key from any other table makes the load fail instead of touching it. A lock timeout of 10 seconds keeps a stuck reader from queuing the public API behind the load.

## Dumps

| File | Holds |
| --- | --- |
| `axonarium.json` | Every record, as a `KnowledgeBase` (valid against the schema) |
| `retractions.json` | The retractions log |
| `<table>.csv` | One per table; arrays and JSON parts as JSON text, booleans as `true`/`false`, nulls empty |
| `edges.graphml` | The edge graph: a node per entity, an edge per row of `edges` with its counts and strength |
| `manifest.json` | Schema version and row counts per table |

JSON-LD and Parquet dumps wait for the release job (sprint 3.2).

## Continuous integration and deployment

- **CI:** the `checks` job gains a Postgres 17 service container. A step "Migrate and rebuild an empty database" runs `alembic upgrade head`, `alembic check` and the build against it, and the build's database tests run there too (`AXONARIUM_TEST_DATABASE_URL`).
- **Deploy:** a new workflow, `deploy.yml`, runs on pushes to `main` in the `production` environment (secrets for `main` only). It runs `alembic upgrade head`, builds, and loads Supabase using the environment secret `SUPABASE_DB_URL`. Without the secret it builds the dumps only, with a notice. It never runs on pull requests.

## Dependency

SQLAlchemy 2.1.3, Alembic 1.20.0 and `psycopg[binary]` 3.3.6 (SQLAlchemy's Postgres driver), in a new `build` dependency group: the standard tools for table definitions, migrations and loading. Recorded in ADR 0008, with the decision to serve read-shaped tables rather than LinkML's normalized DDL: LinkML's object store failed on this schema, and its surrogate-key tables would make an awkward REST API. The generated DDL stays as the schema's reference SQL.

## Tests

- Edges: aggregation, exclusion of retracted claims, strongest strength, sorted distinct arrays, disputed counts.
- Dumps: the valid tree's `axonarium.json` validates as a `KnowledgeBase`; CSV round-trips row counts; GraphML parses; two builds give byte-identical output; a failed validation writes nothing and leaves an existing `--out` untouched.
- Database (run when `AXONARIUM_TEST_DATABASE_URL` is set, always in CI, after the migrations): a load gives the expected row counts and a sample row; it never changes the schema; a second load replaces, never duplicates; a load that fails part-way leaves the previous data intact; a view on a table survives; a foreign key from another table makes the load fail safely; a missing column names the migration step; the migration gives `anon` select and nothing else.
- Safety: a failed load never shows the password, however the URL is written; tests never see an exported `AXONARIUM_DATABASE_URL`; `--out` may not be the working folder, overlap `data/`, or hold files that aren't a previous build; a record field with no column is an error; data files hold only JSON values (`json-value`, a new `checks files` rule).
- CLI: exit statuses and output.
